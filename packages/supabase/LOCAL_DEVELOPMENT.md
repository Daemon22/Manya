# Local Development Guide for @manya-os/supabase

This guide explains how to set up and run the @manya-os/supabase package locally for development and testing.

## Quick Start

### Option 1: Automated Local Setup (Recommended)

The Manya-OS project includes an automated setup script that starts an embedded PostgreSQL instance, applies migrations, and provides a Supabase-compatible API surface.

```bash
# From the Manya-OS root directory
node scripts/setup-local-supabase.js
```

This script:
- Starts embedded PostgreSQL on port 15432
- Downloads and configures PostgREST (Supabase-compatible REST API)
- Applies all migrations automatically
- Sets environment variables for testing
- Keeps the process running for manual testing

The script will output environment variables like:
```
SUPABASE_URL=http://localhost:15433
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

### Option 2: Manual Local PostgreSQL

If you prefer to use your own local PostgreSQL instance:

```bash
# 1. Start PostgreSQL (using Docker as an example)
docker run --name manya-postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=manya_dev \
  -p 5432:5432 \
  -d postgres:16

# 2. Create a .env file in packages/supabase/
cp packages/supabase/.env.example packages/supabase/.env

# 3. Edit .env with your configuration:
SUPABASE_URL=http://localhost:5432  # or your Supabase project URL
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
SUPABASE_DB_URL=postgresql://postgres:postgres@localhost:5432/manya_dev
SUPABASE_MIGRATE_ON_START=true

# 4. Run migrations programmatically
# See the "Running Migrations" section below
```

## Running Migrations

### Automatic Migration on Startup

Configure your application to run migrations automatically when it starts:

```typescript
import { configFromEnv, SupabaseClientFacade } from '@manya-os/supabase';
import { ConsoleLogger } from '@manya-os/supabase';

const config = configFromEnv();
const logger = new ConsoleLogger('info');

const facade = new SupabaseClientFacade(config, logger);
await facade.ready(); // Waits for migrations to complete
```

### Manual Migration Execution

For more control over when migrations run:

```typescript
import { configFromEnv, SupabaseClientFacade, MigrationRunner, PostgresMigrationExecutor } from '@manya-os/supabase';
import { ConsoleLogger } from '@manya-os/supabase';

const config = configFromEnv();
const logger = new ConsoleLogger('info');

// Create a direct PostgreSQL executor for fresh databases
const executor = new PostgresMigrationExecutor(config.databaseUrl!);

const facade = new SupabaseClientFacade(config, logger);
const runner = new MigrationRunner(
  facade.getClient(),
  logger,
  config.migrationDir,
  executor, // Use direct SQL executor for fresh databases
);

const results = await runner.runPending();
console.log(`Applied ${results.length} migrations`);

// Clean up
await executor.close();
facade.dispose();
```

## Environment Configuration

### Local Development

For local development, your `.env` file should look like:

```bash
# Using the automated setup script (recommended)
SUPABASE_URL=http://localhost:15433
SUPABASE_SERVICE_ROLE_KEY=<generated by setup script>
SUPABASE_ANON_KEY=<generated by setup script>
SUPABASE_DB_URL=postgresql://postgres:postgres@localhost:15432/manya_test
SUPABASE_MIGRATE_ON_START=true
```

### Production

For production deployment, use environment-specific configuration:

```bash
# Production configuration (set via your deployment platform)
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<from Supabase Dashboard>
SUPABASE_DB_URL=<private PostgreSQL connection string>
SUPABASE_MIGRATE_ON_START=true
```

**Important:** Never commit production credentials to version control. Use your deployment platform's secret management (e.g., Vercel Environment Variables, AWS Secrets Manager, etc.).

## Testing

### Unit Tests

Unit tests run without a database connection:

```bash
npm test -- --testPathPattern=packages/supabase/tests/unit
```

### Integration Tests

Integration tests require a real database. Two options:

**Option A - Using the automated setup:**

```bash
# Terminal 1: Start the local environment
node scripts/setup-local-supabase.js

# Terminal 2: Run integration tests
npm test -- --testPathPattern=packages/supabase/tests/integration
```

**Option B - Using a remote Supabase project:**

```bash
# Set up environment
cp packages/supabase/.env.example packages/supabase/.env
# Edit .env with your Supabase credentials

# Run integration tests
SUPABASE_INTEGRATION_TEST=true npm test -- --testPathPattern=packages/supabase/tests/integration
```

## Architecture Overview

The database/migration backbone uses a single codepath for both local and production environments:

```
Application Code
       ↓
Environment Configuration (.env / config object)
       ↓
SupabaseClientFacade
       ↓
MigrationRunner (shared logic)
       ↓
MigrationSqlExecutor (environment-specific)
       ├─ PostgresMigrationExecutor (local/production PostgreSQL)
       └─ Supabase RPC fallback (existing databases)
       ↓
Database (local PostgreSQL or production Supabase)
```

### Key Components

1. **Environment Configuration** (`config.ts`)
   - Reads from environment variables or config object
   - Validates required fields
   - Provides defaults for optional fields

2. **SupabaseClientFacade** (`client.ts`)
   - Wraps the Supabase client with lifecycle management
   - Optionally runs migrations on startup
   - Provides `ready()` method to wait for initialization

3. **MigrationRunner** (`migrations/runner.ts`)
   - Shared migration logic (works in all environments)
   - Reads migration files from disk
   - Tracks applied migrations in `schema_migrations` table
   - Executes pending migrations in order

4. **PostgresMigrationExecutor** (`migrations/postgres-executor.ts`)
   - Direct PostgreSQL connection for migration execution
   - Used for fresh databases before RPC helpers exist
   - Server-side only (never exposed to clients)

## Troubleshooting

### Migration Fails with "exec_sql RPC not found"

This error occurs when trying to run migrations on a fresh database without a direct PostgreSQL connection. Solutions:

1. **Set `SUPABASE_DB_URL` or `DATABASE_URL`** in your environment
2. **Use `PostgresMigrationExecutor`** when running migrations manually
3. **Apply migrations manually** via the Supabase SQL Editor first

### Connection Timeout

If you experience connection timeouts:

1. Check that your PostgreSQL instance is running
2. Verify the connection string format
3. Increase `SUPABASE_TIMEOUT_MS` if needed
4. Check firewall/network settings

### Migration Already Applied

If a migration fails with "already applied" but you need to re-run it:

1. Check the `schema_migrations` table in your database
2. Manually remove the entry if you're certain it's safe
3. Re-run the migration

## Security Best Practices

1. **Never commit `.env` files** - Add `.env` to `.gitignore`
2. **Use service-role keys server-side only** - Never expose to clients
3. **Use separate databases for dev/staging/prod** - Avoid mixing environments
4. **Rotate credentials regularly** - Especially after security incidents
5. **Use row-level security (RLS)** - Enforce access control at the database level
6. **Audit migration execution** - Monitor who/when migrations are run
